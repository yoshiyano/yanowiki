# アクセス権の評価

権限ファイルの記録から、そのページのアクセス権を決める手順と関数です。

## アクセス権を評価する

画面のいちばん下の「アクセス権を評価する」（既定では閉じている）にページ名を入れると、
そのページで何が許されるかを表で確かめられます。初めて開いたときはトップページの表を出します。
記録は書き換えません。

表に並ぶのは次の行です。

| 行 | 中身 |
|---|---|
| 未認証 | 未ログイン。未登録のIDも判定の上では同じ答えになる（`_user_principals` が None を返す）ので、1行で足りる |
| 一般の認証済みユーザ | 架空の行。ログインしているが、管理者・助手でもなく、名指しされた許可者にもカスタムグループにも当たらない立場（`auth.explain_privilege_generic`）。`g:all` に当たるので、未認証と答えが違うことがある |
| このページに直接影響するアカウント | 当たった行（`config/privileges`・`config/privileges.plugin` の R・W）にログインIDとして名指しされているか、書かれたカスタムグループのメンバーである人（`privilegesui._affected_uids`）。`g:all`・`g:any` は展開しない。管理者・助手というだけでは出ない |

- 結果は「閲覧・編集」「閲覧のみ」「不許可」と出す（`PAGE_WRITE`/`PAGE_READ`/`PAGE_NONE`）
- 閲覧・編集それぞれの「当たった行」は、ページだけで決まるので表の上に1回だけ出す
  （`auth.page_privilege_rules`）。`config/privileges.plugin` の当たった行があれば併記する
- 各行にアカウントの状態（管理者・助手・ロック中・承認待ち）を添える。ロック中・承認待ちは
  判定の上では未認証と同じなので、色を変えて目立たせる（`userdb.is_locked`・`userdb.is_approved`）
- 判定は `auth.explain_privilege`（`page_privilege(...).check(...)` と同じ決めかたを、当たった
  行までさかのぼれるようにした版）に任せる。大量判定用の `PagePrivilege` は使わない。
  system・plugin をそれぞれ判定し、返り値は `system`／`plugin` キーに分かれる
- 記録の読み直し（`privilege_records.load`・`load_plugin`）は、表を作る1回の呼び出しにつき1回だけ
  （`rows`／`plugin_rows` 引数で使い回す）

## 判定の関数（`auth.page_privilege`）

ログインIDを渡して判定器を作り、`check` でページ名ごとのアクセス権を聞きます。

    privilege = auth.page_privilege(wiki_dir, "alice")   # 記録・アカウント・所属グループを1回だけ読む
    privilege.check("Tech/Secret")                       # → "W" / "R" / "-"
    [privilege.check(p) for p in pages]                  # 複数ページも check を回すだけ

- 未ログインなら `None` か空文字を渡す。記録に無いID・ロックされたアカウントも未ログインと同じ
- **管理者・助手も特別扱いしません。** 規則に名指しされていなければ一般のアカウントと同じ答えです
- 複数ページ用のメソッドは置いていません。下ごしらえは判定器を作るときに済んでいるので、
  メソッドにしても速くならないためです

ワイルドカードは「`*` 以外の部分の長さ」ごとの辞書に分け、ページ名の先頭（末尾）をその長さで
切り出して引きます。手間が規則の数ではなく長さの種類の数で決まります。5000ページでの実測
（2026-09-14）で、ほかの方式と比べて選びました。

| 規則の数 | 1件ずつ呼ぶ | 規則を1つずつ `startswith` | 正規表現にまとめる | **長さ別の辞書（採用）** |
|---|---|---|---|---|
| 10件 | 約1400ms | 8ms | 10ms | **5ms** |
| 400件 | 約6380ms | 107ms | 458ms | **8ms** |
| 2000件 | — | 521ms | — | **13ms** |

**1つのページに同じ種類の行が複数当たるときは、いちばん具体的な指定を使います。**

- 完全一致は、どのワイルドカードよりも優先
- ワイルドカード同士は、一致したルール文字列（`*` 以外）が長いほうが優先
- 同じ具体さの行（`Tech/Secret` に `Tech/*` と `*ecret` がどちらも当たる、など）は許可者を合わせる。
  それより具体さの低い行は、内容にかかわらず使わない（`auth._matching_rule`）
- 記録ファイルは保存のたびに並べ直すので、「あとの行が勝つ」という決まりは持たない

`Tech/*` で広く絞り、`Tech/Secret` だけさらに絞る、`Tech` の完全一致の行で入口だけ開ける
（`Tech:R:g:any`）、といった書きかたができます。`Tech*`（`/` の無い前方一致）は `TechNotes`
なども含みます。

## `config/privileges.plugin` との優先順位

`#readauth`・`#writeauth` が書き出す記録も `auth.page_privilege` の判定に入ります。
手で書く `config/privileges`（system）より**優先**されますが、**緩和する方向には働きません**
（設計者の指示、2026-09-23）。

    sys_priv = privilege(page, user)          # config/privileges だけで見た答え
    plg_priv = privilege_plugin(page, user)   # config/privileges.plugin だけで見た答え
    priv = 厳しいほう（`-` > `R` > `W`）

- plugin 側に記録が無ければ plugin 側は `W`（制限なし）なので、system の答えがそのまま通る
- plugin の記録があれば、system より厳しい答えを持ち込める（「優先」）
- plugin が system より緩くても採用されない（「緩和しない」）。`#readauth` で絞ったページを、
  `config/privileges` を緩めて開放することはできない

plugin 側は完全一致だけが当たるので、system 側の「いちばん具体的な指定」とは干渉しません。

## 検索での判定

`search_matches` は、候補を決める段（`candidate_subpaths`）の直後で閲覧できないページを落とします。
本文を流す前なので、落とした分は本文を読みません。判定器 `privilege` は `search_matches` などの
必須の引数です。件数の表示（「N件中…」）も落としたあとの数にします（そうしないと件数の違いから
隠したページの存在が漏れるため）。
