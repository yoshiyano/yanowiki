# AI エージェントに Wiki ページを書かせる

#code()

**AI エージェント（Claude Code など）にこのシステムの Wiki ページを書かせるときの要点集**です。
エージェントに渡す指示書として、そのまま読ませることもできます。
`git clone` で取得した wikiSystem だけで使えるように、手元の特定の Wiki には頼らずに書いてあります。

**どの型のプロジェクトにも共通して最も効くのは次の 3 つです。**

1. **ChangeLog に「なぜそうしたか」と失敗を残す**
2. **同じことを 2 か所に書かない**（片方からリンクする）
3. **リンクを機械的に検査する**（添付の [checklinks.py](/=_system/.attach/Tech/wiki_byAiAgent/checklinks.py)。[6.2](#62-リンクを機械的に検査する)）

## 添付のスクリプト

| ファイル | 何をするか |
|---|---|
| [checklinks.py](/=_system/.attach/Tech/wiki_byAiAgent/checklinks.py) | ページ内のリンク先（ページ名と見出し）が実在するかを検査する。標準ライブラリだけで動く |

wikiSystem のルート（`wiki.py` のあるフォルダ）に置いて使います。

```bash
cd <wikiSystemのルート>
curl -O http://127.0.0.1:8619/=_system/.attach/Tech/wiki_byAiAgent/checklinks.py   # 手元のサーバから取る場合
chmod +x checklinks.py
./checklinks.py <Wiki名>      # 使いかたは 6.2
```

ブラウザからこのページの添付をダウンロードして置いても同じです。`wikidata/` は、置いた場所の `wikidata/`、
カレントフォルダの `wikidata/`、環境変数 `WIKIDATA`、`--wikidata` の順に探します。

## 1. 方針 — wiki が正

| | 何を書くか |
|---|---|
| コード | 要件を中心とした、簡潔で必要不可欠なコメントだけ |
| wiki | 動作理解・修正に必要なコメントを足したコード + そのあとに詳細な説明。開発記録と、使う人向けの情報サイトを兼ねる |
| git | コード中心。導入方法・簡単な使いかた程度。詳細な資料は置かない |

- **正は wiki の 1 つだけ。**GitHub Wiki 等へ出すときは、wiki から**スクリプトで一方向に変換して転記**する（[6.7](#67-外部へ転記するとき)）
- **転記先で手直ししない。**次の転記で上書きされて消える。転記先向けの文言差し替えもスクリプト側の表に持たせる
- 例外: **運用・管理寄りでは、動いている実物（サーバの設定ファイル等）が正**のことがある。wiki には中身を写さず「どこを見れば確かめられるか（サーバ・ファイルの場所）」と記録日を書く

## 2. 置き場所と反映

### 2.1 ディレクトリ

```
<wikiSystemのルート>/wikidata/<Wiki名>/
├── wiki/      ← ページ本体（.md）。直接編集する
├── pageinfo/  ← 目次・検索用 DB（wikiall.db、自動生成）
├── attach/    ← 添付ファイル
└── config/    ← Wiki ごとの設定
```

- Wiki は [新しい Wiki を作る](/NewWikiGuide) で作れる。**書き始める前に `ls wikidata/` で Wiki 名を確かめる。**作業を頼まれたときの名前が打ち間違いのことがある（`3vj3room` → 実在は `evj3room`）。似た名前があれば、どちらに書いたかを ChangeLog と報告に書く
- ディレクトリがそのままページ階層になる

```
wiki/index.md                → /              （トップ）
wiki/ToDo.md                 → /ToDo
wiki/Spec/index.md           → /Spec          （フォルダの目次）
wiki/Spec/Clock.md           → /Spec/Clock
wiki/ChangeLog/2026-09-08.md → /ChangeLog/2026-09-08
```

- **拡張子 `.md` は Markdown、`.txt` は PukiWiki 記法。**
- **新しく作った Wiki には、記法の選びかたによって PukiWiki 記法の雛形 `wiki/index.txt` と `wiki/mainmenu.txt` がある**（`config/default.example.yaml` の `edit.defaultwiki` が `pukiwiki` のため）。Markdown で書くなら、**中身が雛形の文言だけであることを `cat` で確かめてから `.txt` を消し、`.md` を置く。**同名の `.txt` と `.md` を並べない
- Web 画面の「新規ページ」も既定は PukiWiki。その Wiki の `config/default.yaml` の `edit.defaultwiki` を `markdown` にすれば変わる（編集画面ツールバー右端でページごとにも選べる）

### 2.2 添付ファイル

**ページ名と同じ階層の `attach/` の下に置く。**直接置けば取り込み操作なしで配信される。

```
attach/Spec/Network/network.svg
  → ページ /Spec/Network の添付
  → URL: /=<Wiki名>/.attach/Spec/Network/network.svg
  → ページ側: #img(network.svg)  /  ダウンロードのリンクは [network.svg](/=<Wiki名>/.attach/Spec/Network/network.svg)
```

**フォルダの目次ページ（`wiki/X/index.md` → `/X`）の添付は `attach/X/index/` に置く。**`attach/X/` に置くと `#img()` が `img plugin error` になる（`_sys/wikilib/attach.py`。トップ `wiki/index.md` の添付が `attach/index/` なのと同じ規則）。

```
attach/Design/index/architecture.svg
  → ページ /Design（wiki/Design/index.md）の添付
  → URL: /=<Wiki名>/.attach/Design/index/architecture.svg
```

### 2.3 編集したら `updatepage` で取り込む

目次・検索・更新履歴・`#ls()` は DB 側にあるため、**直接編集したら毎回実行する。**

```bash
cd <wikiSystemのルート>
./wiki.py updatepage =<Wiki名>            # その Wiki の全ページ
./wiki.py updatepage =<Wiki名>/ToDo       # 1 ページだけ
./wiki.py updatepage --force =<Wiki名>    # 一致・不一致に関わらず入れ直す
```

出力例: `[MyWiki] 更新: ToDo` / `ページの取り込み: 更新1 追加1 (1 Wiki, 0.28秒)`

**自動取り込みもある**（`_sys/wikilib/pagesync.py`。仕組みは [平文ファイルの取り込み](/Tech/UpdateDB)）:

| いつ | 何を取り込むか |
|---|---|
| サーバ起動時 / 起動から 1 時間ごと | 全 Wiki の追加・書き換え・削除 |
| ページを開いたとき | DB に無いページの**追加だけ**（書き換えは取り込まない） |
| `./wiki.py updatepage` | 指定 Wiki の追加・書き換え・削除 |

- **先に自動で取り込まれたページは `updatepage` の出力に出ない。**出てこなくても慌てず DB を見る

  ```bash
  cd wikidata/<Wiki名>/pageinfo
  python3 -c "import sqlite3; [print(r) for r in sqlite3.connect('wikiall.db').execute('select subpath, path from pages')]"
  ```

- **自動取り込みを当てにしない。**書き換えは最長 1 時間反映されず、その間はリンク検査も古い DB を見る

### 2.4 ページ名の制約

| 使えない名前 | 理由 |
|---|---|
| `=` で始まる | Wiki の指定に使う記号 |
| `.` で始まる | システムのファイル |
| `memo.md` のような拡張子形式 | 添付ファイルと区別が付かない |

## 3. ページ構成の型

**役割で分けると、どこに書くか迷わない。**共通の 4 つを置き、性格に応じて足す。

### 3.1 どのプロジェクトでも要るもの

| 場所 | 役割 | 書くこと |
|---|---|---|
| `index` | トップ | 何のプロジェクトか、ページ構成、関連 GitHub など総括。**人の呼びかたの表（[5.1](#51-共通の原則)）もここに置く** |
| `mainmenu` | サイドメニュー | 全ページへの導線 |
| `ChangeLog/YYYY-MM-DD` | 日々の記録 | **何をしたか + なぜそうしたか + 失敗** |
| `ToDo` | やること | 進行中・未着手・決めていないこと |

- `submenu` を置くとサイドバーの 2 枠目になる（外部リンク・関連資料向き）
- ChangeLog と ToDo は役割で分ける（**済んだことは ChangeLog、これからは ToDo**）

### 3.2 読み手で分ける

**同じ機能でも読み手が違えば別ページにする。**

| 読み手 | 知りたいこと | 書かないこと |
|---|---|---|
| 使う人 | 画面の見かた、操作、何ができるか | 内部構造、API 名 |
| 組み込む人 / 導入する人 | 導入手順、関数と引数、設定値 | 実装の経緯 |
| 開発する人 | 構成、ビルド、テスト、運用ルール | 使いかたの初歩 |

機能が複数系統あるなら「読み手 × 機能」の 2 軸で分け、**共通の入口ページ（「どれを読めばよいか」の表だけ）から機能別へ振り分ける。**入口に中身を重複させない。

```
UsageGuide          使いかた（共通の入口）
  2way/UsageGuide     機能別の使いかた
Embedding           組み込み方法（共通・配布物・導入手順）
  2way/Embedded       機能別 API リファレンス
DevGuide            開発の進めかた
```

### 3.3 性格ごとに足すページ

**機器・システム寄り**（実機がある、現場で作業する）

| 場所 | 書くこと |
|---|---|
| `Spec/*` | 決めたことと理由。**実測値** |
| `Dev/*` | そのページだけ辿れば作業できる手順書 |
| `Code/*` | コメント付きコード + 説明 |
| `Parts/*` | データシートの要点、外部資料の添付と概略 |

**ソフトウェア・ライブラリ寄り**（配布する、他人が組み込む）

| 場所 | 書くこと |
|---|---|
| `UsageGuide` | 使う人向け。画面の見かた、操作 |
| `Embedding` | 導入手順、配布物、共通事項 |
| `<機能>/Embedded` | API リファレンス（関数・オプション・戻り値の表） |
| `DevGuide` | ディレクトリ構成、ビルド、テスト、Git 運用、リリース手順 |
| `Roadmap` | 大きな機能単位の段階計画と現在地 |

`Roadmap` は大きな機能単位、`ToDo` は段階計画に載らない小さめ・横断的なタスク。**両方に同じ項目を書かない**（使い分けを ToDo 冒頭に明記しておく）。

**運用・管理寄り**（既存設備を調べて記録する）

| 場所 | 書くこと |
|---|---|
| `Spec/*` | 聞き取った・調べた事実。**分からないところは「未記録」と明記** |
| `ToDo` | **まだ記録していない情報**と**確認したいこと**（懸念・なぜ気になるか・確かめかた）の 2 本立て。立ち上げ直後は「調べることの地図」になる |
| `Dev/*` | 実際の作業が出てきてから足す。**空の枠は先に作らない** |

### 3.4 迷ったときの振り分け

| 内容 | 置き場所 |
|---|---|
| なぜ今こうなっているか | ChangeLog（時系列） |
| いまどうなっているか | Spec / Roadmap（現在形） |
| どうやるか | Dev / DevGuide（手順） |
| どう使うか | UsageGuide（使う人の言葉） |
| どう呼ぶか | Embedded（関数と引数の表） |
| このコードは何をしているか | Code |

**同じ内容を 2 か所に書かず、リンクする。**「後述」などもリンクにする。見出しがアンカーになる（[4.3](#43-リンクとアンカー)）。

## 4. 記法リファレンス

ページは **Markdown**（見出し・表・箇条書き・コードフェンスは一般と同じ）+ **プラグイン**。ここには書く側が踏みやすい点だけを挙げる。全記法は [書ける記法](/Syntax) にある。

### 4.1 プラグインの呼びかた

```
#name()              引数なし（行頭に置くブロック型）
#name(引数)           引数つき
#name(引数){中身}      1 行の中身
#name(引数){{         複数行の中身
中身
}}
&name(引数){中身};     インライン型（文中。& で始めて ; で終わる）
```

- **`#` のあとに空白を入れない**（Markdown の見出しになる）。**インラインは `;` を忘れない**（ただの文字列になる）
- 引数はカンマ区切り。位置指定・`名前=値`・混在が可。値にカンマを含めるなら引用符で囲む。途中を飛ばすなら `#ls(, , TITLE)`
- **`{{ … }}` の中身はページ改名時のリンク自動修正の対象外。リンクは中身の外に置く**

### 4.2 よく使うプラグイン

**`#code()` — コードの色付け**

- **ページ冒頭（タイトル直下）に `#code()` を単独で置く。**これがあるページだけ、コードフェンスに Prism.js のハイライトとコピーボタンが付く
- 普通のコードフェンス（```` ```python ````）と `#code(python){{ … }}` は同じ見た目。**中身に ```` ``` ```` を含むときだけ `#code()` を使う**
- 引数: 第 1 引数 = 言語名（`python` `bash` `json` `javascript` 等）、`nonum` = 行番号なし、`nocopy` = コピーボタンなし

**`#note()` — 目立たせる枠**

~~~
#note(type=warn){{
複数行の中身。空行も可。**太字** や [リンク](/Spec) などそのページの記法が書ける
}}
~~~

| `type` | 用途 |
|---|---|
| `warn` | 踏むと痛い落とし穴、壊れる操作、制約（最も多用） |
| `info` | 補足、背景、判断の理由 |
| `tip` | ちょっとした便利情報 |

`label="注意"` で左上の文字を変えられる。

**`#ls()` — ページ一覧**（フォルダの目次ページの末尾に置く）

```
#ls()                              自分の下を名前順
#ls(Tech)                          Tech フォルダ
#ls(, sort=FNAME_REV)              名前の逆順（ChangeLog 向き。新しい日付が上）
#ls(Tech, recursive, MTIME_REV)    下の階層まで、更新の新しい順
```

引数: `folder`（常に 1 番目、既定は自分の下）/ `recursive` / `sort`（`FNAME`（既定）・`MTIME`・`SIZE`・`TITLE`、`_REV` で逆順）/ `format`（既定 `BOTH`）

**`#contents()` — ページ内目次**。`#contents()` で 3 階層、`depth=2` で 2 階層。サイドバーにも目次が出るので、**長いページの本文中に置きたいときだけ**使う。

**`#img()` — 画像**（添付として置き、ファイル名で参照）

```
#img(network.svg)                          そのまま
#img(教室のネットワーク構成>network.svg)      図の下にタイトルを出す（推奨）
#img(photo.jpg, right){{                    右に置いて文章を回り込ませる
回り込ませる文章
}}
#img(photo.jpg, w50%)                      表示幅の半分
```

図を積極的に使って読みやすくする（描きかたは [5.9](#59-図--svg-で描きpng-にして確かめる)）。

**`#glossarytip()` — 用語にマウスを載せると説明が出る**（仕組みは [用語のツールチップ](/Tech/GlossaryTooltip)）

- ページ内に**定義リストで用語集**を書き、`#glossarytip()` を 1 行置く。効くのはそのページ内だけ
- **用語集はページ末尾に置き、冒頭から見出しへリンク**する（スマートフォンでは説明が出ないことが多いので、文字で辿れるように）
- 用語はそれを主に使うページに 1 回だけ書く（複数ページに書くと片方が古くなる）

```markdown
# ネットワーク

**このページが何なのか。**用語は[ページ末尾](/Spec/Network#用語)にまとめてあります。

#glossarytip()

## 構成図
（本文）

## 用語

DHCP
: 端末がつながったときに、IP アドレスなどの設定を自動で配る仕組み
```

一致の規則（`plugin/glossarytip.js` で確認）:

| 規則 | 注意 |
|---|---|
| 大文字小文字を区別 | `DHCP` は `dhcp` に付かない |
| 前後が ASCII 英数字・`_` だと一致しない | `DHCPv6` の中の `DHCP` には付かない。**日本語に挟まれていれば付く**（`端末用HUB`） |
| 説明は `<abbr title="…">` で出す | **タップでは出ないことが多い** |

**そのほか**: `#recent()`、`#ref()`、`#hr()`、`#br()`、`#color()`、`#size()`、`#ruby()`、`#katex()`、`#vote()`、`#tasklist()` など。

**この Wiki システム固有の記法（`#recent()`、`#ls()` など中身が生成されるもの）は転記先では動かない。**外部へ出すときは節ごと落とすか静的な一覧に置き換える。

### 4.3 リンクとアンカー

ページへのリンクは **先頭の `/` から**書く: `[時刻管理](/Spec/Clock)`、`[ドリフト補正](/Spec/Clock#ドリフト補正)`

**見出し ID の作られかた**: ①小文字にする ②空白をハイフンにする ③英数字・かな・漢字・ハイフン・アンダースコア以外（記号）を消す

| 見出し | ID |
|---|---|
| `## main.py` | `mainpy` |
| `### Web 画面から確認・変更する` | `web-画面から確認変更する` |
| `## kumiko（172.22.23.1）` | `kumiko17222231` |
| `## 1. 権限を確かめる` | `1-権限を確かめる` |
| `## マージ: `toHunks` / `applyMerge`` | `マージ-tohunks--applymerge`（**ハイフン 2 つ**） |
| 2 つ目・3 つ目の `## 使いかた` | `使いかた-1`、`使いかた-2` |

- **罠 1: 記号は消えても、その両側の空白はハイフンとして残る**（ハイフンが連続する）
- **罠 2: 同じ見出しが再出すると連番が付く。**同じ見出しを並べず「2 文書の使いかた」のように見出しだけで場所が分かる書きかたにする
- **アンカーは手で組み立てず、検査スクリプト（[6.2](#62-リンクを機械的に検査する)）で検証する**
- この規則はこのシステムのもの。GitHub 等の転記先は規則が違う（[6.7](#67-外部へ転記するとき)）

## 5. 中身の書きかた

**記法より、何を書くかで価値が決まる。**

### 5.1 共通の原則

- **結論を太字にする。**読み飛ばしても要点が拾えるように
- **数値を出す。**「速くなった」ではなく「1.0 秒 → 0.3 秒」。測っていないなら「実測していない」と書く
- **推測は推測と書く。**断定と推測が混ざると後から検証できない
- **表を使う。**比較・設定値一覧・症状と対処は散文より速く読める
- **失敗を書く。**最も価値がある。成功談だけの資料は同じ罠を防がない
- **専門用語には説明を入れる。**一般のユーザ前提の表現に。怪しい表現は早めに依頼者のチェックを受ける（用語集は `#glossarytip()` で本文を長くせずに満たせる）
- **用語を決めて全部揃える。**別の言葉で呼ぶと別物だと思われる。**用語を変えるときは「画面に出る文字」「コード中のコメントと docstring」「wiki の全ページ」の 3 か所を同時に直す。**表記の決めごと（カッコを半角に、等）は `DevGuide` か `Spec` に 1 行書いておく

**情報の確かさを 4 つに書き分ける**（聞き取りから始めるとき特に）:

| 確かさ | 書きかた | 置き場所 |
|---|---|---|
| 聞き取った・実測した事実 | 「〜です」と現在形 | `Spec` |
| 分かっていない | **「未記録」と明記。空欄にしない**（空欄は「無い」「関係ない」と読まれる） | `Spec`（その場）+ `ToDo`（一覧） |
| 数値から計算した値 | 「〜台から計算すると〜。実物は未記録」 | `Spec` |
| 一般論から考えた懸念 | 「未確認」と明記し、**なぜ気になるか・確かめかた**を添える | `ToDo` の「確認したいこと」 |

**製品の一般的な仕様を、この環境の事実のように書かない。**例: 「KMS 認証は 180 日で切れる」（仕様）/「この教室では起動が少ないので切れやすい」（推測）/「実際に切れているか」（未確認）を 1 文に混ぜない。確かめて事実になったら `ToDo` から `Spec` へ移す。

**人の呼びかたを分ける**（混同を指摘されて全ページ直した実例あり）。**作業を頼む人**と、**作ったものを使う人**を別の言葉で呼ぶ。次は一例で、プロジェクトごとに決めてよい。

| 書きかた | 指す人・もの |
|---|---|
| **依頼者** | AI エージェントに作業を依頼・指示し、判断する人 |
| **読み手・使う人** | 作ったもの・設備（画面、ライブラリ、端末など）や、wiki を読む人 |
| root 権限、sudo の権限 | 権限のこと。**「管理者権限」とは書かない**（Wiki の「管理者」など人の呼びかたと混ざる） |

- **wiki のトップページにこの呼びかたの表を置く**
- 会話やメモの言葉を wiki に写すときは、どちらの意味か必ず読み替える

### 5.2 ChangeLog — なぜそうしたか

- **1 日 1 ページ、ファイル名 `YYYY-MM-DD.md`**
- 書くこと: 何をしたか / **なぜそうしたか** / **迷って選ばなかった案とその理由** / **失敗とその原因**
- 失敗は **症状 → 原因 → なぜそうなっていたか → どう直したか** の順。**「なぜそうなっていたか」を飛ばさない**（そこに再発防止がある）

```markdown
## `install.py` が 5 個のファイルを落としていた

配置後に確認したら、実機に **8 個しか無かった**。にもかかわらず「セットアップ完了」と表示していた。
原因は配置順を決める定数。（コード）
**`ORDER` が「置くものの一覧」を兼ねていた。**モジュールを増やしたときに足し忘れた。（直したコード）
**加えて、配置後に実機のファイル一覧と数え合わせるようにした。**
```

目次ページ `ChangeLog/index.md`:

```markdown
# ChangeLog

開発の記録です。日付ごとにページを分けています。

#ls(, sort=FNAME_REV)

## 記録のしかた

- 1日1ページ。ファイル名は `YYYY-MM-DD.md`
- **何をしたか**だけでなく、**なぜそうしたか**を残す
- 迷った末に選ばなかった案も、理由とともに書いておく
```

- **見出しの日付は、システムから渡される「今日の日付」をそのまま使う。**前回のファイル名や会話の区切りから類推・インクリメントしない。書く前に `ls` で既存ファイルを確かめ、今日のファイルがあれば追記する

### 5.3 「やらないと決めたこと」も残す

却下した案を ToDo から消すだけにすると、理由が残らず同じ提案が蒸し返される。

1. **ChangeLog に、調べたこと・結論・理由を書く**（本体。調べた過程も書く。前提が変わったとき再検討できるように）
2. ToDo から該当項目を消す
3. Roadmap の「これから」からも外し、「作らない」と明記する

例: 「サンプルを GitHub Pages で開けるようにする」→ **見送り**（Pages は private リポジトリからでも公開サイトになり、「自分だけ」の要件を満たせない）

### 5.4 Spec — 決めたことと理由

- **現在形で書く**（「〜にしました」ではなく「〜です」）
- **各決定に理由を添える**（例: 「ソケットタイムアウトは **1 秒**（旧実装の 10ms は短すぎる）」）
- **実測値の節を作る。**見出しに「いつ・何で・どれだけ測ったか」を入れる（例: `## 実測（2026-09-08、lc01a・15.9 時間・97 回）`）。**仕様・見立てと実測が食い違ったら、それも書く**
- ソフトウェアでの「実測」は、テスト件数・ベンチマーク・対応ブラウザなど。いつ測ったかを添える

### 5.5 使いかた（UsageGuide）と API リファレンス（Embedded）

ソフトウェア配布では Spec の代わりにこの 2 つを置く。

**UsageGuide**

- **使う人の言葉で書き、関数名・クラス名は出さない**
- 画面の説明は色や位置など**「見えるもの」で**書く（表: 「左が赤い行 | 文書 A から削除された行」）
- **説明が「記号の意味」から始まるなら、その表示自体を疑う**（diff 由来の `-`/`+` 記号は使う人に伝わらず廃止した）

**Embedded**

- **表が主役。**引数・既定値・意味を 1 行ずつ

```markdown
## `render(target, left, right, options?)` → handle

| オプション | 既定 | 意味 |
|---|---|---|
| `merge` | `false` | 取り込み操作ボタンを出す |

戻り値のハンドル:

| メンバ | 内容 |
|---|---|
| `getMergedText()` | 現在の編集コラムのテキスト |
```

- **「結果をどう受け取るか」を必ず書き、入口から出口までの短い呼び出し例を 1 つ添える。**関数一覧だけでは使う人が辿り着けない

### 5.6 Dev / DevGuide — 上から辿れば作業できる

- **そのページだけ読んで作業が完了すること。**全体像は 1 枚で読めるよう簡潔に、詳細は必要に応じて他ページへ
- **「うまくいかないとき」の表を必ず付け、実際に踏んだエラーメッセージをそのまま載せる**（検索で辿り着ける）
- **人が物理的にやること**（ボタンを押しながら電源投入など）は節を分けてはっきり書く（例: `### 実機のそばにいる人にお願いすること`）
- DevGuide も同じ: ディレクトリ構成・ローカル起動・テスト・リリース手順を上から辿れる 1 枚に

```markdown
# 新しい個体をセットアップする

**新品を使える状態にするまでの手順**です。経緯は ChangeLog にありますが、このページだけで導入できます。

#code()

## 用意するもの
（表）

## 1. ○○する
（コマンド）

## うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `failed to access /dev/ttyUSB0` | `picocom` が掴んだまま。`lsof` で調べて `kill` |
```

### 5.7 Code — コメント付きコード + 説明

- **実際のコードにコメントを足したものを載せ、そのあとに説明。**コード本体には経緯を書かないので、思考経緯はここが唯一の説明になる
- **コードは抜粋でよい**（全文だと要点が分からない）。一番気を使った部分を中心に、守っていることを小見出しで説明し、落とし穴は `#note(type=warn)` に
- **参照は行番号でなく関数名・定数名で書く**（「`side-by-side.js` の `sideCells()`」）。行番号は 1 回のリファクタで全部ずれる。行番号は滅多に変わらないコード（確定仕様、外部定義）に限る
- 目次ページには**「読む順番」**（動きを追う順）を書く

### 5.8 Roadmap — ToDo を段階で区切る

**ToDo を箇条書きで終わらせず、段階（Phase）で区切ると、1 ページで Roadmap（全体の地図と現在地）を兼ねる。**

```markdown
# ToDo

やることの一覧です。終わったものは [ChangeLog](/ChangeLog) に記録します。

## Phase 1 — WiFi と Web 経由ファイル更新

- [x] 仕様をまとめる（[Phase1 Web更新](/Spec/Update)）
- [x] 実機での通し確認（壊れた `boot.py` からの復旧まで確認）

## Phase 2 — 時刻管理と表示

- [x] **DS1302 の ppm 実測** → **26.7ppm**（ticks_ms は 49.6ppm）
- [ ] 長時間運転での安定性確認

## Phase 3 — 時報とアラーム（完了）

## Phase 4 — CH7800

- [ ] 部品の入手
```

効く理由と決まり:

1. **着手順の理由が残る**（順序の理由は ChangeLog 初日に書く）
2. **全体像と現在地が 1 ページで見える。**未着手の段階も書く。別ページにすると二重管理になる
3. **済んだ段階を消さない。**見出しに「（完了）」と書き足す。**チェック済み項目には実測値や結論をそのまま書く**
4. **段階に入らないもの**（横断的作業、判断待ち「決めていないこと」、急がないもの）は自然と別節になる

- **段階は機能で切らず「これが終わると何が楽になるか」で切る**（例: Phase 1 Web 更新 → シリアルを繋がずに開発できる）
- **「全部できないと何も動かない」計画にしない。**途中で止まっても使えるものが残るように
- **計画を変えたら、変えたことと理由も書く。**黙って反映しない（例: `**2026-08-28 に順序を変更（依頼者の指示）:** …`）
- 規模が大きければ `Roadmap` を独立させてよい。その場合も**先頭に現在地**（例: `**現在地（v1.1.1）: … すべて実装済み。**`）、各段階に「実装済み / これから」
- **迷ったら ToDo に埋め込む形から始める**（手狭になってから分ければ間に合う）

### 5.9 図 — SVG で描き、PNG にして確かめる

- **構成図は SVG で描いて添付にする。**アスキーアートは崩れやすく狭い画面で読めない。SVG はテキストなので直しやすい
- 背景は白い四角で塗る（テーマの色に左右されない）/ 図の下に**凡例**（実線・点線・点線枠の意味）/ `#img(タイトル>ファイル名)` で何の図かを出す
- **描いたら PNG にして自分の目で見る**（ソースを読むだけでは文字の重なり・はみ出しに気付けない）: `convert network.svg network.png`（ImageMagick）
- **`font-family` の先頭に日本語フォントを書く**（例: `font-family="'Noto Sans CJK JP', sans-serif"`）。`sans-serif` だけだと ImageMagick が日本語の字形の無いフォントを選び、**PNG から日本語がすべて抜ける**。手元の日本語フォントは `fc-list :lang=ja family` で調べる
- 行の途中だけ `<tspan>` で太字にすると文字が重なった（ImageMagick 描画時）→ 行ごと太字にする。**描く道具で結果が変わる書きかたは避ける**
- **図にも確かさの書き分けが要る。**線・矢印・配置は文章より強く事実に見える。**分かっていない接続は線を引かず、枠の中に「接続位置は未記録」と文字で書く**

## 6. 品質を保つ仕掛け

### 6.1 ページを足したら導線を張る

**リンクを張らないと誰も辿り着けない。**まとめるページからリンクし、統括的なページならトップとメニューからも辿れるようにする。

- `index.md` — 資料の一覧表に 1 行足す
- `mainmenu.md` — リンクを足す。**特に重要なページは太字**（緊急時に目が行く）

```markdown
## メニュー

- [トップ](/)
- [ChangeLog](/ChangeLog)
  - [2026-09-08](/ChangeLog/2026-09-08)
- [ToDo](/ToDo)

### 開発

- [開発環境](/Dev)
  - [**壊れたときの直しかた**](/Dev/Recovery)
```

### 6.2 リンクを機械的に検査する

添付の [checklinks.py](/=_system/.attach/Tech/wiki_byAiAgent/checklinks.py) を使う。`pageinfo/wikiall.db` の各ページの目次（見出しと ID）と突き合わせる。**`updatepage` を実行してから使う**（DB が古いと直したリンクが切れて見える）。

```bash
cd <wikiSystemのルート>
./checklinks.py <Wiki名>              # 複数指定も可
./checklinks.py --all                 # 全 Wiki
./checklinks.py --wikidata <フォルダ> <Wiki名>   # wikidata の場所を指定する
```

```
[MyWiki] リンク不良 1 件
  MyWiki/3way/Embedded.md:147  /2way/Embedded#表示エリアの高さ-viewh   … 見出しが無い
```

終了コードは、不良なしが 0、リンク不良ありが 1、使いかたの誤りが 2。

検査対象から除外しているもの（どちらも実際に誤検出した）: **コードフェンス・インラインコードの中**（記法説明の例）、`/=別Wiki/…` と `/.xxx`（他 Wiki・システムページ）。**同じページの中だけのリンク（`](#見出し)`）と、添付のリンク（`](::file)`）は検査しない。**

### 6.3 コードと事実も機械的に検査する

**リンク検査を通っても、コード例は古くなる。**（消えた関数名、使っていない関数、旧実装を手で簡略化したもの、が残っていた実例あり）。この検査は、プロジェクトごとにその場で小さなスクリプトを書く。

- コード例はコメントを足すので完全一致は求めない。**字面が変わったら wiki も直すべき行 — `def` 行、大文字の定数、`import` — だけを拾い、ソースに同じ字面があるか見る**

  ```python
  PAT = re.compile(r"^\s*(def \w+\(|[A-Z_]{3,} = |from \S+ import |import \S+$)")
  ```

- ファイル名（`` `foo.py` ``）と CLI オプション（`` `--force` ``）も照合する。**オプションは `--help` と突き合わせ、サブコマンドのヘルプも集める**（忘れると実在するものを「無い」と誤検出）
- **用語を言い換えたら、古い語が残っていないかも検査する。**一括置換は必ず取りこぼす
- **実在しなくてよいもの（未実装の設計案、旧実装の引用、意図して残した例）は理由つきで除外リストに入れる。**理由が無いと次の人がまた調べ直し、毎回の報告に本物が埋もれる

  ```python
  ALLOW = {"def _talk(frame):": "Phase 4 の設計案。まだ実装していない"}
  ```

- **検査は 0 件になるまで繰り返す。**直した結果が別の食い違いを生む。検査スクリプト自体の誤りも疑う（甘い検査の「合格」は信用できない）

### 6.4 書き直したらリンク元も見る

**見出しを消す・改称すると、そこへのリンクが切れる。**改称（用語統一、見出しに項目を足す、「未着手」→「実装済み」）が最も切れやすい。**節を書き直したら、特に用語を統一したら、必ず検査を回す。**

### 6.5 ToDo に状態を持たせる

```markdown
- [x] 終わったこと（リンク付きで、どこに記録があるか示す）
- [~] 進行中（下位項目で内訳）
- [ ] 未着手

## 決めていないこと

| # | 項目 | いつ決めるか |
|---|---|---|
| 1 | 主時刻源をどちらにするか。実測データで再判断する | Phase 2 完了後 |
| 4 | ~~ファームを更新するか~~ → **2026-09-07 に更新済み** | 決着 |
```

- **判断待ちは「決めていないこと」の表に分ける**（埋もれない）
- **決着したら消さずに取り消し線で残す**（判断の経緯が追える）。「やらない」で決着したものは [5.3](#53-やらないと決めたことも残す) の手順で ChangeLog へ

### 6.6 版数・数値の散らばり先を決める

- バージョン番号やテスト件数は気付かないうちに複数ページへ散る（v1.1.1 リリースで 4 ページ書き換えが必要だった）
- **`DevGuide` のリリース手順に、更新すべき wiki ページを列挙する**（例: 「Wiki のバージョン記載を更新: index / Roadmap / DevGuide / Embedding」→「リンク検査を回す」）
- **そもそも数字を書く場所を減らす。**「現在 `'1.1.0'`」ではなく「`build.py` が埋め込む」と書く。**数字はそれ自体が情報のときだけ書く**

### 6.7 外部へ転記するとき

転記用のスクリプトは、プロジェクトごとに書く。やること:

| やること | なぜ |
|---|---|
| 転記しないページ（ChangeLog など）を除く | 公開先に日々の記録は要らない |
| 除いたページへのリンクを別の場所（Releases 等）へ向け替える | リンク切れを残さない |
| ページ名の読み替え（`index`→`Home` ほか） | 転記先の命名規則 |
| `](/Page#anchor)` を絶対 URL へ | 転記先にこのシステムの解決規則が無い |
| 転記先だけの文言差し替え | 転記先に無いもの（「更新記録」等）への言及を直す |
| **リンク検査。1 件でも切れていたら転記しない** | 壊れたまま公開しない |

- **アンカーの変換規則を推測で実装しない。**このシステムは `mdit_py_plugins`、GitHub は github-slugger で規則が違う（連続空白を 1 ハイフンに畳む自前実装でリンクを壊した）。**転記先に実際に描画させて付いた id を読む**:

  ```bash
  gh api -X POST /markdown --input - -H "Accept: application/vnd.github.html+json"
  # 返った HTML の id="user-content-…" がそのままアンカー
  ```

- **文言差し替えは表で持ち、左辺が見つからなければエラーで止める。**黙って読み飛ばすと、元の文が変わったとき差し替えが効かないまま公開される

### 6.8 表示を実際に確かめる

**リンク検査 0 件でも、画像の配信やプラグイン JS の読み込みは分からない。**動いているサーバから取って確かめる。ポートは `config/server.yaml` の `port`（雛形 `config/server.example.yaml` の既定は `8619`）。

```bash
W=http://127.0.0.1:8619/=<Wiki名>
# ページが返るか
for p in "" Spec/Network ToDo; do curl -s -o /dev/null -w "%{http_code} /$p\n" "$W/$p"; done
# 画像の参照先と配信時の種類
curl -s "$W/Spec/Network" | grep -o '<img[^>]*>'
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" "$W/.attach/Spec/Network/network.svg"
# プラグイン専用の JS・CSS が読み込まれているか
curl -s "$W/Spec/Network" | grep -oE '/\.plugin/[a-z]+\.(js|css)' | sort -u
```

- ブラウザでの見た目（用語説明が出るか等）は curl では分からない。図は PNG にして見る。それ以外は依頼者に見てもらうか、**確かめていないことを報告に書く**
- curl で開いたページもアクセス記録（`log/access.log.db`）に残る
- サーバが動いていない場合は、依頼者に起動してもらうか、起動してよいかを確かめる

## 7. よくある失敗（チェックリスト）

| 失敗 | 対策 |
|---|---|
| 伝えられた Wiki 名をそのまま使った | `ls wikidata/` で確かめる |
| 雛形 `index.txt` を残して `index.md` を足した | 中身を見てから `.txt` を消す |
| `#` のあとに空白 / インラインの `;` 忘れ | 見出し・文字列になる。`#note(...)`、`&note(...){…};` |
| 冒頭に `#code()` が無い | コードに色が付かない |
| `{{ }}` の中にリンクを書いた | 改名時の自動修正対象外。中身の外に置く |
| アンカーを手で組み立てた / 記号両側の空白を忘れた | 検査スクリプトで確認。ハイフンが 2 つ並ぶことがある |
| フォルダの目次ページの添付を `attach/X/` に置いた | `attach/X/index/` に置く（[2.2](#22-添付ファイル)） |
| `updatepage` を忘れた | 目次・検索・`#ls()` に出ず、検査も古くなる |
| `updatepage` の出力に無いページを「取り込めていない」と思った | 自動取り込み済みのことがある。DB を見る |
| ページを足してメニューを直さなかった | 誰も辿り着けない |
| 同じ説明を 2 か所に書いた | 片方が古くなる。リンクで繋ぐ |
| 成功した話しか書かなかった | 失敗こそ書く |
| 用語が揺れたまま | 画面・コード注釈・wiki を同時に直す |
| 作業を頼む人と、使う人を同じ言葉で書いた | 呼びかたを分け、トップに表を置く |
| 分からない項目を空欄にした | 「未記録」と書く |
| 製品の一般仕様を、この環境の事実のように書いた | 「未確認」と明記して ToDo へ。確かめてから Spec へ |
| 図に分かっていない接続の線を引いた | 描かずに「未記録」と書く |
| 見出しを改称してリンクを放置 | 検査を回す |
| コードを行番号で参照した | 関数名で参照する |
| 却下した案を黙って消した | 理由を ChangeLog へ |
| 転記先で手直しした | スクリプト側の表に入れる |
| リンク検査だけで表示を確かめなかった | curl で取る |

## 8. 1 ページ作るときの流れ

```bash
# 0. Wiki 名を確かめる（新しい Wiki なら雛形の .txt も確認）
cd <wikiSystemのルート>
ls wikidata/

# 1. 書く
vi wikidata/<Wiki名>/wiki/Spec/NewThing.md

# 2. トップとメニューを直す
vi wikidata/<Wiki名>/wiki/index.md wikidata/<Wiki名>/wiki/mainmenu.md

# 3. 取り込む
./wiki.py updatepage =<Wiki名>

# 4. リンクを検査する
./checklinks.py <Wiki名>

# 5. 表示を確かめる（画像やプラグインを使ったとき）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8619/=<Wiki名>/Spec/NewThing

# 6.（外部へ出しているなら）転記し直す
```

ページの雛形:

~~~markdown
# タイトル

**このページが何なのか**を 1〜2 行で。

#code()

## 最初の見出し

（本文）

#note(type=warn){{
**踏むと痛いこと**をここに。
}}
~~~

## 9. どこから始めるか・参考ページ

**まず ChangeLog から始める。**空の枠を先に作るより、書くことが溜まってから整理するほうが続く。

| 型 | 始める順 |
|---|---|
| 機器 | ChangeLog → Dev（手順）→ Spec（決めごと）→ Code |
| ソフトウェア | ChangeLog → UsageGuide → Embedded（API）→ DevGuide |
| 運用・管理 | ChangeLog → Spec（現状。未記録を明記）→ ToDo（調べること）→ Dev（作業が出てきたら） |

**Roadmap は早めに作る**（溜まってからでは「何を決めていなかったか」を思い出せない）。最初は ToDo を段階で区切るだけで十分。1 行目に「段階 1 が終わると何が楽になるか」を書ければ、それが Roadmap。
