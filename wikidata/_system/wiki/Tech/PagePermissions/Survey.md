# 調査の時点の検討

仕組みを決める前の調査で検討した論点と、その結論です。

## 調査の時点の検討

2026-09-13（`dev`、Ver 1.0 / Rev 107）の調査で挙げた論点と、その後の結論です。

### 1. プラグイン由来の記録は「描画時」に作る

`#readauth` などの記録は描画のときに作ります（設計者の判断、2026-09-13）。

> プラグイン由来のアクセス制限の記録を描画時以外とすると、本体側に特殊な処理が必要になるため
> 修正漏れなどにつながる懸念から避けたい。Webでの編集後は必ず表示を行うため更新ができる。

退けた案は「保存時に作る」です。画面からの保存はすべて303でそのページの表示に戻るので、
Webで編集したページは保存した直後に必ず描画されます。本体が `#readauth` の名前や引数の意味を
知らずに済む点でも、描画時のほうが筋が通ります。

一度も描画されていないページ（ファイルを直接置いて取り込んだページ）の穴は、**取り込んだ
ページをその場で1回描く**ことで塞ぎました（`wikilib.pagesync.review_page`）。描くと本文が
書き換わるプラグインに備え、描く前と後が一致するまで描き直します。上限は
`pagesync.MAX_REVIEW`（5回）で、打ち切ったページは「落ち着かなかったページ」として取り込みの
結果に出します。描画で例外が出ても取り込みは止めません。費用は、159ページの
`updatepage --force` で 6.3秒 → 8.3秒でした。

### 2. sqlite かテキストか

**テキストにしました。** 行が独立しているので壊れた行だけを捨てられ、目で見て直せます。
決め手は、差分の履歴（下の (a)）に乗せられることです。

| 壊れかた | テキスト | sqlite |
|---|---|---|
| 書き込み中に落ちる | 一時ファイルへ書いて `rename` すれば原子的 | ジャーナル/WALで同等 |
| ディスクの部分的な不良 | 壊れた行だけを捨てられる | B-treeのページが壊れると、ぶら下がる行がまとめて読めない |
| 人が手で壊す | 起こりやすい | 起こりにくい |
| 壊れたあと直せるか | 目で見て直せる | `.recover` などの道具が要る |

壊れて読めなかったときは、全部拒否ではなく、制限なしとして動き続け、管理者に見えるところへ
警告を出す考えです（全部拒否だとサイトが開けなくなるため）。

`config/` 配下の控えは、形式にかかわらずまだありません（`dbbackup` が見ているのは
`pageinfo/wikiall.db` だけ。`users.db` も同じ）。作るとすれば次の2つです（「これから足すもの」）。

- **(a) 変えた履歴を残す**: `backup` 表のキーは subpath という文字列なので、`=config/privileges`
  のような予約キーで権限ファイルの差分も積める。差分はテキスト同士でしか取れない
- **(b) 壊れたときに戻す**: `dbbackup` の日次の控えの対象を `config/` 配下へ広げる。いまの
  `healthy()` は sqlite 専用なので、テキスト向けの確認を足す

### 3. 当たるルールが複数あるとき

→ いちばん具体的な指定を使い、同じ具体さの行は許可者を合わせます。`privileges.plugin` は
優先するが緩めない形です（上の「判定の関数」「`config/privileges.plugin` との優先順位」）。

### 4. `R` と `W` の関係

調査の時点では「`W` は `R` を含む」と決めました（`W` にだけ書いたときに「編集できるのに読めない」
という書き間違いが効かないようにするため）。→ 2026-09-21に「R と W を別々に判断し、書けるのは
読める人だけ」へ変わりました。

### 5. ユーザ名で書くと、IDを変えたときに孤児になる

許可者はログインIDで書くので、`/.admin/accounts` でIDを変えると、その行は誰も指さなくなります。
グループ（`g:GROUP`、中身は `uidnum`）で書けばこの問題は起きません。
→ **まだ決めていません。** いまはIDを変えても権限ファイルは書き換わりません。

### 6. その他の論点の結論

| 論点 | 結論 |
|---|---|
| 記録が無いページの既定・全体の既定をどこで決めるか | 設定ではなく `config/privileges` の既定の行（`*`） |
| 誰がこのファイルを編集できるか | `/.admin/privileges` は管理者と助手だけ。ページの編集者は `#readauth`・`#writeauth` で自分のページの制限を足せる |
| 編集できる人は、自分に閲覧権限を書ける | 「ページ編集者が権限を与える」とおりで意図どおり。そのため編集側を先に締めた |
| 階層の継承 | 継承の仕組みは作らず、ワイルドカードと「いちばん具体的な指定」で表す。子の完全一致の行でフォルダの指定を上書きできる |
| プリンシパルに個人を足すか | `u:` などは付けず、ログインIDをそのまま書く（`Tech/Secret:R:alice,g:staff`） |
| 存在を隠すか、中身だけ隠すか | **存在は見せる**（設計者の判断、2026-09-15）。直接開くと、無いページではなく403になる。一覧（`#ls`・`#recent` など）と検索結果からは省く |
| 添付ファイル | 持ち主のページの閲覧権限を当てる。閲覧できなければ404 |
| いまのプラグイン（`#readauth`）をどうするか | 廃止でも併存でもなく、権限の仕組みへの書き出し元にした（描画時に `config/privileges.plugin` へ書く）。`#viewable_period` は権限とは別の軸で、検索との関係は**まだ決めていない** |
